# tools/ · 歌词自动化

## 曲包校验（`validate_packs.mjs`，2026-11-17 夜）

```powershell
node tools\validate_packs.mjs             # 查 public/songpacks，逐包列出 issue
node tools\validate_packs.mjs --strict    # warn 也算失败（发布前用）
node tools\validate_packs.mjs --dir .tmp\某个包
```

- 校验逻辑**只有一份**：`src/songpack/schema.ts`（迁移 + 默认值 + 校验），程序运行时
  （`loader.ts`）和这个脚本都 import 它。脚本能直接跑 `.ts` 靠的是 Node 22+ 的类型剥离。
- 查得出：schema 版本、`id` 和目录名不一致、必填项缺失、**字段拼错**（给最像的名字）、
  asset 登记了但文件不存在、`actions.json` 的时间越界/缺 clip、`index.json` 和目录对不上、
  JSON 带 BOM。
- 格式说明（字段表 / 默认值 / code 列表 / 迁移策略）见 `docs/pack-schema.md`。

## 总入口（`pipeline.py`）

一条命令跑完造曲包的全部步骤，并维护 `<pack-dir>/job.json` 状态机：

```powershell
python tools\pipeline.py `
  --pack-dir public\songpacks\demo `
  --audio "D:\Music\song.mp3" `
  --lyrics-src "D:\Music\song.lrc"
```

| 阶段 | 产物 |
|---|---|
| `pack` | `pack.json`（时长和 BPM 都从音频实测） |
| `lyrics` | `lyrics.json`（`.lrc` / `.txt` / `.json` 统一转过来） |
| `separate` | `stems/vocals.mp3` + `stems/instrumental.mp3` |
| `f0` | `work/f0.json`（参考音高：跟唱判定 / 和声音程 / 待机哼歌都读它） |
| `align` | `lyrics.auto.json` |
| `units` | `lyrics.units.json` |
| `choreo` | `actions.json` |

- **歌词是必需输入**。没有歌词只能走「无歌词路径」（文字准确率 39%），那条还没接进来；
  缺了它会直接报错停下，而不是跑到第四步才崩。
- **`.lrc` 走快速路径**：歌词自带时间戳 → `align` 整段跳过，省掉几分钟 ASR。
  `.txt` 没有时间戳，需要跑 ASR 对齐。
- 产物存在且状态是 done → 跳过；产物被删 → 自动重跑
- `--only choreo` / `--from units` 只跑一部分（会把选中阶段的状态清回 pending，
  否则「从某步重跑」会被跳过），`--force` 全量重跑，`--dry-run` 只打印命令
- 失败会把子进程最后 40 行写进 `job.json`，界面上能直接看到原因
- `job.json` 是原子写的（临时文件 + `os.replace`），前端可以放心每秒轮询

**打包分发时要排除 `job.json` 和 `work/`。**

### 耗时参考（204.6s 的歌，8 线程 CPU）

| 阶段 | 耗时 |
|---|---|
| pack | ~1s（含 BPM 检测） |
| lyrics | <0.1s |
| separate | **~85s**（2.5× 实时，纯 CPU） |
| f0 | ~2s（`extract_f0.py`，只看人声轨） |
| align（LRC 时跳过） | 0s / 否则 2–3 分钟 |
| units | ~1s |
| choreo | ~2s |

所以「有 LRC」约 1.5 分钟，「只有 txt」约 4–5 分钟。分离是唯一的大头。

## 和声的起音片段（`cut_attack.py`）

和声那条线是「持续元音循环 + 每个 mora 换一次音高」，本身没有辅音。
要让它「唱出字」，只能靠从真人声里切一小段**起音瞬态**，在每个 mora 开头替换掉循环。

```powershell
python tools\cut_attack.py     # 重切 public/voices/att_ra_{mid,hi}.wav
```

- `att_ra_mid.wav`：对白「から」的 ら（`shots/ref3/sep/ref3_vocals.wav` 17.184 s），
  305.6 Hz，90 ms。闭塞只有 **6 ms**，紧跟 burst + 元音头。
- `att_ra_hi.wav`：翻唱里**唱的** ら（`shots/cover90s40.wav` 64.97 s），535.8 Hz，
  90 ms，前 40 ms 是闭塞。
- **踩过的坑**：旧的 `harmony_att.wav`（124 ms）**切反了**——0–98 ms 是上一个字的元音，
  98 ms 才是闭塞。当头播等于先唱一个字再闭嘴，怎么调参数都不可能像 ら。
  量包络（2 ms 网格、看 −12 dB 以下的最长连续段）才发现这件事。
- 两段按目标音高挑：低于 ~405 Hz 用 mid、高于用 hi，变调不超过 ±4.5 个半音
  （变调会连共振峰一起动，跳太多就换人了）。

## 和声的循环音色库（`make_pitch_variants.py` + `build_loop_library.py`，2026-11-15）

和声靠 `playbackRate` 变调——**共振峰跟着一起走**。库里只有 258–575 Hz 六段，
而白花唱到 895 Hz，那一段就是 +7.7 个半音的「花栗鼠」。

```powershell
python tools\build_loop_library.py --apply     # 补库：6 段 → 24 段（210–850 Hz）
python tools\make_pitch_variants.py --wav public/voices/loop_575.wav --shifts 3,6 --check
```

- `make_pitch_variants.py`：**TD-PSOLA** 保共振峰变调。按周期（period）把波形重新摆一遍，
  每个 grain 都是原波形的复制 → 基频变了、频谱包络不变。输出长度仍是整数个周期，
  接缝靠「环绕折叠 + 窗和归一」保证。
  - 关键实现：grain 中心咬到**波峰**（±0.25 周期内找最大峰）而不是等间隔，
    否则相位噪声会摊到每个周期上；
  - 实测（`--check`）：音高误差 ≤4 音分，共振峰位移 **−0.3…+0.4 个半音**，
    而对照组（重采样）是 **+2…+6 个半音**——这就是这个工具存在的理由。
- `build_loop_library.py`：贪心插空隙（始终补最大的那个），直到 196–900 Hz 内
  任意目标离最近采样 **≤1.2 个半音**。生成 18 段新的 + 保留原 6 段，
  最后写清单 `public/voices/loops.json`（运行时读它，`?loops=legacy` 回老六段做 A/B）。
- **家族**：同一段原始采样派生出来的几档在 json 里写 `familyRootHz`。
  运行时同一家族只让离目标最近的一档发声（同时响会拍频 = 用户报过的
  「一个音高两个声音」），混合只发生在不同家族之间。
### 换元音（`--seed` / `--vowel`，2026-11-15）

和声原本只会发「あ」：库里所有循环都是 `--vowels a` 筛出来的，所以**嘴上是 い/う/え/お、
声音永远是 あ**。要让她「唱字」，得先有别的元音。

```powershell
# 1) 从真实翻唱里切一段「え」（白花 190.5 s 那段，467 Hz）
python tools\make_harmony_voice.py --audio shots/coverfull.wav --out public/voices/loop_e_465.wav `
  --min-hz 455 --max-hz 475 --vowels e --units <pack>/lyrics.units.json `
  --match-curve public/voices/timbre-target.json
# 2) 用 PSOLA 铺到现有「あ」库的每个音高上（24 段一段不落）
python tools\build_loop_library.py --seed public/voices/loop_e_465.wav --vowel e --apply
```

**为什么一段真音就够**：元音的身份在**共振峰（绝对 Hz）**，TD-PSOLA 只改基频、不动
频谱包络——把 467 Hz 的「え」搬到 300 或 800 Hz，读起来还是「え」。所以不必每个元音
每个音高都录一遍。

**为什么不是「同一元音多段混合」**：整族都派生自同一个种子，`familyRootHz` 相同，运行时
只让最近的一档发声（否则同一条音高叠几遍会拍频）。代价是「え」比「あ」薄（あ 有 6 个
家族混合），这是当前已知的取舍。

运行时按 `lyrics.units.json` 的 `v` 逐字切换（`HarmonyVoice.setVowel`，60 ms 交叉淡化），
`?vowel=off` 退回「全程あ」做 A/B；没录到的元音（现在 i/u/o）自动退回「あ」。

- 顺带修的 bug：权重原来是 `exp(-(d/sigma)²)` 直接归一，`sum < 1e-6` 时所有增益判 0
  → 目标音高远离所有采样时（高音区）和声**整个哑掉**。改成先减最小值再取指数。

### 重造整库（`rebake_loops.py` + `apply_loops.py` + `qa_loops.py`，2026-11-17）

用户指出「低音区和高音区都相当不稳定」。查下来不是音高（24 档偏差 ≤6.3 音分），
是**相位被反复 OLA 涂抹**：相邻周期波形相关，原始素材 0.981 / 派生 1 代 0.910 /
派生 2–3 代 0.897，而音域两端正好是链条最深的地方。

```powershell
python tools\rebake_loops.py --all --out .tmp\rebake-full --keep-raw   # 每档 SVC 直出（~40 分钟）
python tools\qa_loops.py .tmp\rebake-full                             # 音高/相位/电平/元音验收
python tools\apply_loops.py --from .tmp\rebake-full --dry              # 干跑：锁音高后会写到哪
python tools\apply_loops.py --from .tmp\rebake-full                    # 装库 + 改 loops.json + json
node scripts\ensure-dist.mjs --force                                   # dist/voices 是 public 的拷贝
```

- `rebake_loops.py`：给 SVC 一个**目标音高的长音源**（`user_a*.wav` 那条 3.8 s），
  seed-vc 保音高只换音色 → 每档第一代长音（0.65 s），没有链式派生。
  - `steady_window` 必须带「窗口内最小帧 RMS ≥ 0.35 × 最响帧」的硬条件，否则会挑中换气处
    （第一版 14 档出来 20–71% 是静音）；
  - `--keep-raw` 存完整 SVC 输出，之后想换裁剪长度不用重跑 SVC（一次 40 分钟）。
- `apply_loops.py`：**锁音高用谐波梳**（`.tmp/comb.py`），不用 pyin —— pyin 在这批 0.65 s
  样本上偏 −5…−6 音分，而运行时按 json 的 `rootHz` 算 `playbackRate`，写偏就唱偏。
  另外做整周期裁剪 + 交叉淡化、电平对齐到被替换那一档、写 json 与 `loops.json`。
  **家族号不动**（6 个家族 = 混音 6 个声部，改家族数会变厚度/糊度，不是这次要改的）。
- `qa_loops.py`：音高/相位/电平/频谱质心（元音一致性）四列，`ok`/`BAD` 一眼能扫。
- **换源修元音（2026-11-17 夜，352/384）**：SVC 的输出音色会被**源素材**带跑。用 269 Hz 那条
  长音上采样当源时，324–384 这几档出来泛音塌、共振峰偏（352 高 4.2 半音 / 384 低 9.0 半音）。
  修法：拿**该档自己的旧样本**按周期拉长到 1.44 s 当源，SVC 只把相位重合成干净的一代
  （352 包络回 +0.35 半音、384 +0.15，相位相关 0.964/0.992）。
  另外**步数不是越多越好**：352 在 24 步泛音更准，384 在 40 步包络更准，量了再定。
- 试听包：`tools/ab_audition.py` → `shots/loop-audition-fix/`（旧 / 旧拉 3× / 新，等长 4 s）。

### 查「和声链脏在哪」：抓输出 + 逐层关（2026-11-17 夜）

离线量采样查不出「接续时不够干净」，得拿**链的真实输出**。为此加了两个调试钩子
（只在 `__pet` 上，不参与正常播放）：

```powershell
# 页面里（CDP 探针）：
#   __pet.harmonyTone(392)                把和声钉在某个音高
#   __pet.attTest(0.26, 'consonant')      触发一次真实咬字（vowel / consonant / aspirate）
#   __pet.hset({dbl: 0, dblLfo: 0.0022})  运行时改参数（一次启动切多个变体）
#   __pet.captureHarmony(2.6)             抓 2.6 s 原始输出（Int16 base64 + 采样率）
```

- `captureHarmony` 用 `ScriptProcessorNode` 直抄 float，**不用 `MediaRecorder`**——
  后者是 opus 有损，正好会把要查的细小毛刺压掉。
- 判据用三条，别混：**谐波 vs 谐间比**（周期信号的能量应全在谐波上）、
  **包络 1–6 Hz 起伏峰峰值**（「晃」）、**相邻样本 |Δ| 离群**（「咔嗒」）。
- ⚠️ 不要用「周期同步平均残差」：48 kHz 下 392 Hz 的周期是 122.45 个样本，取整会
  每周期滑半样本，平均下来模型自己抹平——第一版就量出 −0.0 dB 的假结果。
- 这一轮的结论：稳态有 **8.9 dB** 的 2–5 Hz 抖动，来源是**双声部副本的延迟抖动**
  （18 ms 延迟 = 55 Hz 梳状滤波，±2.2 ms 的 LFO 让梳齿扫过谐波）。默认降到 0.0002
  → 3.4 dB；`?dblLfo=0.0022` 回旧行为。咬字本身的凹陷（ら 15.1 dB/90 ms、
  は 18.7 dB/65 ms）是替换式咬字的固有代价，不是「脏」。
- 拉长工具 `tools/stretch_loops.py`：TD-PSOLA 按周期重复，**现在库里用了它**——
  2026-11-17 夜按用户建议把 24 档 0.65 s 拉成 **×3 ≈ 1.9 s**（音色差中位 0.24 dB、
  接缝 0.16×99.9 分位、断口 0%），目的是让「原样重来」的周期从 0.65 s 变长。
  代价：a 库从 1.3 MB 涨到 3.9 MB。回退：备份在 `.tmp/voices-065`，
  `python tools\stretch_loops.py --factor 3 --apply` 可重跑；`--only 210,850` 只做几档。
  对比包：`tools/length_ab.py` → `shots/loop-mul/`（short 0.65 s / long 1.9 s）。
- **「え」还没重造**（`tools/rebake_e.py`，已搁置）：`loop_e_*` 同样是链式派生，
  相位相关 0.65–0.88，比旧「あ」还差。试点 210 档正常、850 档量出 293 Hz（锁到分谐波），
  要做得先解决高音档的源。别直接 `--all` 装库。

## 歌词自动化（`fetch_lyrics.py`）

按「标题 + 歌手」搜网易云，拿 LRC。**难点不是下载，是确定是哪一首歌**——
所以这里用**音频时长**做交叉验证：同名翻唱、伴奏版本一大堆，但时长对得上的通常只有一首。

```powershell
python tools\fetch_lyrics.py --query "白花 鈴木このみ" --list          # 列候选
python tools\fetch_lyrics.py --query "白花 鈴木このみ" --auto --duration 230 --out a.lrc
python tools\fetch_lyrics.py --song-id 2117484911 --out a.lrc         # 知道 id 就直接抓
```

- 搜索：`/api/search/get/web?s=<query>&type=1&limit=N`
- 歌词：`/api/song/media?id=<songId>`，`.lyric` 字段就是 LRC
- 两个接口只要浏览器 UA + `Referer: https://music.163.com/`，不需要登录
- 打分：名字像 + 歌手出现在查询里 + 时长接近，三个信号加权；带 `Instrumental` 的扣分
- 应用里「自动找」按钮走的就是这条链路，**列出候选让用户点**，不自动选第一条

接口是网易云网页版自己用的，随时可能失效。失效了就退回「手动存 LRC」，
`parse_lyrics.py` 照样吃得下。

## 音高提取（`extract_f0.py`）

`lyrics.units.json` 里只有 mora 的位置和元音，**没有音高**。歌声合成/音色转换都要它。

```powershell
python tools\extract_f0.py --audio public\songpacks\x\stems\vocals.mp3 `
       --out public\songpacks\x\work\f0.json --plot shots\f0.png
```

算法是 YIN（差分函数 + 累积均值归一化），差分函数用 FFT 自相关算，
230 秒的歌约 **4 秒**跑完。之后有三道清洗：

1. **八度修正**：YIN 的典型错误是算成两倍/一半。某帧和 ±140ms 邻域中位音高
   差接近整八度（log2 比值 1±0.15）就掰回去；
2. **范围闸**：掰完还离邻域一个八度以上、或超出 80–900Hz 的，当噪声置零；
3. **短段清理**：连续浊音不足 3 帧的丢掉（换气口的单帧误判）。

### 白花实测（230.2s）

| 指标 | 数值 |
|---|---|
| 浊音帧占比 | 75.1% |
| 音高范围 | 87–892 Hz（中位 357 Hz） |
| 音符数 | 619（>80ms） |
| 音符总时长 | 134.1s（占全曲 58%） |

**怎么判断它不是噪声**——看音级分布：

```
A# 23.0%   G# 15.0%   C# 13.3%   F 12.5%   C 11.0%   D# 8.3%   D 4.8% ...
前 6 个音级占 83%（噪声约 50%）
半音内偏差 中位 15 cents
```

C#/D#/F/G#/A#/C 正好是 **D♭ 大调**，而且第 7 级 G 只有 0.9%。
噪声不会长成这样。MIDI 中位 65（F4）。

## 歌声合成预览（`sing_synth.py`）

用 F0 + mora 时间轴做**源-滤波器共振峰合成**（不是神经歌声合成）：

- 声源：谐波堆（锯齿波近似），基频来自 `f0.json`，叠加 5.5Hz 微颤音；
- 滤波器：每个元音三组共振峰（F1/F2/F3），把谐波幅度塑形成该元音的音色；
- 时长与断句：来自 `lyrics.units.json`，跨 mora 相位连续（不会每个音咔哒一下）。

```powershell
python tools\sing_synth.py --pack public\songpacks\x --out shots\preview.wav
```

**它做对的是音高、节奏、元音；做不对辅音和换气**，听感在「初代 VOCALOID」那一档。

自查（把合成结果再跑一遍 `extract_f0` 和原曲比）：

```
音高差（合成-原始）中位 +0 cents，|差| 中位 20 cents
  ≤50 cents 75%    ≤100 cents 86%    相关系数 0.654
```

零系统偏移说明没有移调；20 cents 的离散度主要来自我们额外加的颤音。

**混一版带伴奏的**（判断「贴不贴」比听干声有用得多）：

```powershell
python tools\sing_synth.py --pack public\songpacks\x --backing stems/instrumental.mp3 `
       --out shots\mix.mp3 --vocals-out shots\vocal.mp3
```

混音规则（踩过三次坑才定下来）：

1. **先把伴奏峰值收到 0.7**，给要加进来的东西留余量；
2. 人声按 **RMS** 定增益（默认比伴奏低 3dB），不是按峰值——
   合成音的峰值/有效值比很高（每个 mora 起头都是硬边），按峰值定会小得听不见；
3. **不整段缩混音**。前两版就是「混完一削波就整体 ×0.6」，
   结果人声段只提升 0.1dB、空白段倒降 2.8dB，听起来比伴奏还闷。
   现在只压人声的峰值（tanh 软限），最后留 0.62 的余量给 mp3 编码过冲。

白花实测：峰值 0.831（不削波）；混音里「人声段」比「空白段」高 **+3.9dB**，
而同样两段在纯伴奏里只差 -0.8dB——说明人声确实进去了，且空白段是干净的。
产物 `shots/baihua-mix.mp3`（4.4MB）。

### 第二版：连唱 + 共振峰过渡（2026-11-08）

第一版有两处「机械感」的来源，都是可量化的：

**1. 每个 mora 都独立做 20ms 起 + 40ms 落**，连续音节之间出现一次骤降再抬起，
听起来像「一个字一个字念」。现在只有真正断开的地方（间隔 ≥20ms）才做包络，
其余连成一条气。

量化方式：取每对相邻 mora 的交界，算交界前后 ±30ms 的最小 RMS 与两侧的比值
（1.0 = 完全不断）：

| 版本 | 凹陷比中位 | <0.5 的占比 |
|---|---|---|
| v1（每个音都断开） | **0.09** | 100% |
| v2（连唱） | **0.93** | 1% |

**2. 元音是瞬切的**。现在共振峰的**中心频率**在 55ms 内从上一个元音滑过来，
谐波增益按新的中心重新算。

这里踩了一个坑：一开始是「把两个元音的谱包络交叉淡化」，结果 RMS 从 0.061
掉到 0.020——因为包络是在**当前元音的谐波位置**上采样的，换元音后那批频点
正好落在别人的共振峰之间，值掉到 0.03 基线，每个 mora 开头 55ms 几乎没声音。
正确做法是让共振峰自己动（对数频率上插值），谐波增益跟着重算。

### 第三版：辅音（2026-11-08）

前两版只有元音，听感是「一段有音高的元音流」，听不出在唱什么词。现在按假名首字
给每个 mora 加辅音（从 mora 开头切 32–70ms 出来，元音相应缩短）：

| 类型 | 例子 | 做法 | 时长 |
|---|---|---|---|
| 塞音 | か た ぱ が だ ば | 30% 闭塞（静音）+ 8ms 带通噪声爆破 | 32ms |
| 擦音 | さ し は じ | 带通白噪声 + 23Hz 慢调制 | 70ms |
| 鼻音 | な ま | 低次谐波 + 鼻音共振峰(300/1200/2500) | 50ms |
| 闪音 | ら | 低次谐波 + 快速衰减 | 35ms |
| 元音起头 | あ い を | 不加 | — |

验证不是靠听，而是看**每类的高频占比**（首 40ms，4kHz 以上能量）：

```
fric   72%     ← 擦音确实是嘶声
stop   12%     ← 塞音是爆破，高频成分少但短
nasal   0%     ← 浊音，没有高频
vowel  0.3%    ← 基线
```

**交界凹陷**（连唱有没有被辅音打断）现在按类分开看才有意义：

| 类型 | 凹陷比 |
|---|---|
| 元音起头 | 0.96 |
| 擦音 | 0.71 |
| 鼻音 | ~0.6 |
| 塞音 | 0.00（**这是对的**，塞音本来就该有闭塞静音） |

所以这个指标从「机器念字」变成了「有没有按发音方式做对」。

### 第四版：力度与音内衰减（2026-11-09）

前三版的每个 mora 都是同一个电平，整段唱下来能量包络几乎是**一条直线**，
动态只剩辅音那几十毫秒。seed-vc 那边反馈「包络太平」时，一部分根因在这里：

- 逐 mora 力度：长音更响（`1 + min(0.30, (dur-0.28)*0.8)`），再叠 ±6% 的逐音起伏
- 音内衰减：>300ms 的音从 1.0 落到 0.80，>180ms 的落到 0.93（真人唱长音不会一直绷着）
- 塞音闭塞 32→**50ms**，且占辅音段的 60%（之前 30%，几乎形不成凹陷）
- 擦音电平 0.30→0.22（摩擦音和元音的对比拉开）

效果（白花 33–43s，同一句）：

| | 帧能量 < -20dB 占比 |
|---|---|
| 改前 | 4.7% |
| 改后 | **7.6%** |
| 原唱（分离轨） | 17.1% |

### 第五版：辅音提前到拍前（2026-11-09）

前四版把辅音放在 mora 开头，元音因此比 unit 时间晚 32–80ms。真唱不是这样：
拿原唱人声做参照，28 个 mora 的**能量起音比 unit 起点早 27ms**（中位；p25 −101，p75 +79）。

改动：

- 新增 `--vowel-offset`（默认 **0**）：元音落在 unit 时间，辅音整体提前到拍前。
- **前一个元音的尾巴截到下一个辅音的起点**——不然提前的辅音会盖住上一个音，
  塞音的闭塞就不是静音了（第一版改成提前时踩过这个坑，`<-20dB` 直接掉回 0%）。

结果：`<-20dB` 帧 **10.0%**、`<-30dB` **2.9%**（原唱 17.1% / 3.5%）。

### 第六版：辅音按发音方式重做（2026-11-09）

审计发现第三版那套「5 类」的分类本身就有错，不是参数不准：

| 问题 | 白花里的数量 | 后果 |
|---|---|---|
| 浊塞音（が/だ/ば行）当成清塞音 | 37 个 mora | 闭塞用真静音 + 噪声爆破，听起来是 か/た/ぱ |
| 破擦音（ち/つ）当成塞音 | 14 个 | 只有 8ms 爆破（「咔」），没有摩擦段 |
| 破擦音（じ）当成擦音 | 1 个 | 只有嘶声，没有闭塞 |
| づ 完全没处理 | 2 个 | 元音直接起头，没有辅音 |
| ん 完全没处理 | 1 个 | 当成元音（用 'n' 查共振峰表），不是鼻音 |
| っ 完全没处理 | 2 个 | 250ms 近似静音 |

改法（`_KANA_CONS` / `make_consonant`）：

- 新增 `stop_voiced`：闭塞段是**低电平浊音**（前浊）+ 更软的爆破
- 新增 `affricate`：45% 闭塞 + 55% 带通摩擦（ち 4200Hz、つ 5200Hz、じ 3800Hz、づ 5000Hz）
- 新增 `moraic_nasal`（ん）：整个 mora 是鼻音（250/1100/2400Hz），占满时长
- っ：真静音（以前留了一点气声）
- 擦音中心频率也细分了：ふ 1700Hz（[ɸ]）、ひ 3000Hz（[ç]）、ざ行 5000Hz

**没能验证的部分**：想用分离出来的人声轨量「各类辅音的谱重心」来核对参数，
量不出来——分离轨的宽带残留太脏，五类的谱重心都在 2.4–2.7kHz、
4kHz 以上占比都在 18–22%，和元音没有区别。所以上面的中心频率是**按语音学设定**，
不是实测拟合的。

对照试听：`shots/cons-ab.wav`（づ / っ / ん 三处，每处先旧后新）。

### 次谐波修正（`harmonic_fix`，2026-11-08）

白花 8.5–10.3s 那个长音，YIN 给出 **117Hz**，看起来像「唱低了两个八度」。
但逐帧看谱能量：**117Hz 那一档是 0.00**，能量在 467Hz 和 935Hz（=2×467）上。
所以真值是 **B♭4 ≈ 467Hz**，YIN 锁到了 1/4 周期（几个谐波刚好凑成 4 倍周期的重复）。

修法：对每帧只在 `{f, 2f, 3f, 4f}` 里挑，用 **HPS（谐波积谱：各次谐波幅度相乘）**
打分。116Hz 的 HPS ≈ 0（基频没能量），467Hz 的很高，自然选对。只考虑整数倍是刻意的——
次谐波错误几乎总是整数关系。改判前还要求新候选的基频能量超过该帧峰值的 8%，
避免把干净的音改坏。

白花全曲改了 **2692 帧（13.6%）**。改完音级集中度仍是 83%、调性还是 D♭ 大调，
说明没有引入系统性错误。

## TTS 唱法（`tts_sing.py`，2026-11-09）

源-滤波器合成（上面几节）到顶了：把辅音从 5 类改成浊塞音/破擦音/拨音之后，
听感没有变化——问题不是分类，是「用公式造辅音」。换方法：

1. 用本机日语语音（SAPI5 `Microsoft Haruka Desktop`）合成每个假名/每行
   → `shots/tts/kana/*.wav`（53 个）、`shots/tts/lines/*.wav`（27 行）
2. **TD-PSOLA** 把音节改成旋律要求的音高和时长（改音高不改共振峰）
3. 拼回时间轴

实测：F0 跟目标差 **+3.9 cents**，浊音帧 84.7%（原唱 87.1%）。

### 两个已修的坑

- **辅音被替换成元音**：原来对每个输出时刻都找「最近的基音标记」，清音段也照做，
  等于把辅音填成了浊音。现在清音段直接按源位置取一小段原样搬。
- **mora 边界是硬切**：每个 mora 都是独立一段，接缝处一个台阶，频谱上是一排竖条。
  现在连唱处做 12ms 的 sin²/cos² 交叉淡化。

### 失败的尝试：逐行 TTS + DTW

想法：整行 TTS（保住协同发音）→ 用原唱同一行做 DTW 对齐 → 按 warp 重采样。
结果不行，原因很具体：一行语音约 2s，唱出来是 7.6s，DTW 把大量目标帧映射到
**同一个源帧**，长音就成了「冻结的频谱」（频谱图上是一排完美的水平线）。
不解决「长音的元音怎么持续」，这条路走不通。

### 用 Whisper 当听众：可懂度（2026-11-09）

「听不出在唱什么」这件事可以量：把三个版本喂给 faster-whisper small，和歌词的
假名串比编辑距离（CER，越低越可懂）。

| 版本 | 转写 | CER |
|---|---|---|
| 源-滤波器合成 | **空** | **100%** |
| TTS + PSOLA | 「…のことを…」 | **11%** |
| 原唱（分离轨） | 「…」 | 18% |

合成器是**完全不可懂**（Whisper 什么都不输出），TTS 版已经接近原唱的识别率。
副产物：这条指标可以用来量化「改法有没有让字更清楚」，不用每次都靠耳朵。

注意：`faster-whisper` 自带的 `decode_audio` 和当前 PyAV 版本不兼容
（`metadata_errors` 参数），必须先自己解码成 numpy 数组再传给 `transcribe`。

### 已知差距

- 亮度偏低：谱重心 428Hz，原唱 600Hz（Haruka 本身偏暗 + PSOLA 颗粒）。
- 长音还是靠重复颗粒维持，缺自然的衰减/气息；流利度不如合成器。


## 包络移植（`env_graft.py`）

音色转换（seed-vc）那一步的模型输入里**没有源音频的能量**，所以它生成的强弱是
自己猜的，和我们的唱法只是碰巧像。这个工具把源的逐帧能量搬过去：

```powershell
py tools/env_graft.py --source synth.wav --input vc.wav --out grafted.wav
py tools/env_graft.py ... --limit-db 12 --smooth-ms 6   # 更贴，但更可能抽气
```

做法是**只乘一条标量增益曲线**（不改共振峰、不改音高），所以音色几乎不动
（log-mel 距离 1.45→1.47，F0 保持 +1.3 cents）。参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--strength` | 0.8 | 0=不处理，1=完全跟随源包络 |
| `--limit-db` | 6 | 增益限幅，防止把模型的呼吸/气声抹平 |
| `--smooth-ms` | 12 | 增益曲线低通，太短会有抽气感 |

实测（白花 33–43s，2.9ms 帧）：0.47–0.62 → **0.80–0.89**。

**踩过的坑**：`sing_synth` 工作在 **22050Hz**，`env_graft` 工作在 **44100Hz**
（跟 seed-vc 输出一致）。第一版直接复用 `sing_synth.SR` 和它的写文件函数，
结果把 44.1k 的转换结果写成 22.05k，混进 A/B 里就变成了「慢一倍」。

## 内存不足（`mkl_malloc: failed to allocate memory`）

CTranslate2 + MKL 在 Windows 上会按线程数申请 workspace，`small` 模型 8 线程时
可能直接报这个错——**即使机器还有 7GB 可用内存**（桌面端开着 Electron、
两条解码后的音轨时最容易触发）。

`auto_align.py` 现在默认 `--cpu-threads 4`，并且会自动减半重试（4 → 2 → 1）。

**注意降级要覆盖两个阶段**：`mkl_malloc` 不只在 `WhisperModel(...)` 时出现，
也会在**真正开始算**的时候出现——`model.transcribe()` 只返回一个生成器，
开销发生在遍历它的时候。所以重试必须包住「遍历 segments」这个循环，
只包加载是不够的（2026-11-08 就是这样漏了一次：模型加载成功，第一段 encode 就炸）。
现在两处都包了，失败会重新加载更少线程的模型并重跑整段转写，代价是多花几十秒。

流水线里点「重试这一步」即可，已完成的分离不会重跑。

## BPM 检测（`detect_bpm.py`）

```powershell
python tools\detect_bpm.py --audio song.mp3
# BPM ≈ 167.87（置信度 4.41）
#     168.3  score=1.027
#     112.5  score=1.025
#      84.1  score=0.966
```

谱通量包络 + 梳状自相关，只用 numpy（librosa 会带进 numba / soundfile 一整串依赖）。

| 步骤 | 说明 |
|---|---|
| 解码 | 单声道 22050Hz，BPM 不需要高频 |
| 谱通量 | log 压缩后取正向增量，跨频点求和（log 是为了让 hi-hat 和 kick 量级接近） |
| 梳状打分 | 候选速度 L 的分数 = 自相关在 L、2L、3L、4L 的加权和 |
| 先验 | 以 120 BPM 为中心的对数正态，压掉极端速度 |
| 细化 | 抛物线插值到小数 BPM |

**两个必须处理的细节**：

1. **滞后要插值**。96 BPM 对应 53.8 帧、150 BPM 对应 34.45 帧，
   只取 `int(round())` 会让「真实拍点刚好在半帧上」的速度吃亏——
   实测 150 BPM 的节拍器会被判成 75（因为 75 的滞后 68.9 离整数更近）。
2. **置信度不能用 best/median**。自相关有负值，中位数可能是负的，比值会变成负数。
   用 z 分数 `(best - median) / std`。

### 三连音 / 半速的歧义

demo 那首歌实测出来是 **168 BPM**，候选里 112.5（= 168×2/3）和 84.1（= 168÷2）
分数几乎一样。这是音乐本身的性质，不是算法缺陷——同一段鼓点可以数成 168、112 或 84 拍。

所以：

- `pack.json` 里存的是估计值，**用户可以在导入面板点 BPM 徽章手改**
  （改完从 `pack` 阶段重跑）。
- 想让动作更「松」，把 BPM 减半（168 → 84）是合法的选择：
  节拍网格变成半速，弹跳频率减半，编舞乐句长度基本不变（生成器按时间定乐句）。

### 顺带发现的一件事

demo 曲包原来的 `pack.json` 写的是 **96 BPM**，但逐段自相关显示 96 处几乎没有周期性
（0.15 / 0.00 / -0.02 …），168 处则稳定在 0.58–0.73。
也就是说 demo 一直在**错拍**上跳——这大概也是「动作单调」的一个隐藏原因。
现在改成 167.87 了。

## 人声分离（`separate.py`）

UVR MDX-Net ONNX 推理，**不用 torch**。

`audio-separator` 那个包无条件依赖 `torch>=2.3`（不是 extras），
装完 `.pylibs` 会从 276MB 涨到 1GB 以上，pip 解析依赖树实测 14 分钟没结束。
而 MDX-Net 推理本身只需要 onnxruntime —— 这里按 UVR 的参考实现重写了整条链路，
依赖是 **numpy + onnxruntime + PyAV**，全是已有的。

```powershell
python tools\separate.py `
  --audio song.mp3 `
  --model .cache\models\UVR_MDXNET_3_9662.onnx `
  --out-dir out\
```

产出 `vocals.wav` 和 `instrumental.wav`（44.1kHz 立体声 16bit）。

加 `--format mp3` 直接产出能塞进曲包的版本（`--bitrate 192k` 可调）。
204.6s 的歌：wav 36MB → mp3 4.9MB，两条 9.8MB。
两轨走同一条编码路径，编码器延迟一致，所以仍然采样对齐，加在一起就是原混音。

| 项 | 值 |
|---|---|
| 模型 | `UVR_MDXNET_3_9662.onnx`（28MB，`dim_f=2048`）/ `UVR-MDX-NET-Inst_HQ_3.onnx`（63MB，`dim_f=3072`） |
| 来源 | HF `Tha456/uvr5-models`（走 hf-mirror） |
| 参数 | n_fft=6144, hop=1024, dim_t=256, 44.1kHz |
| 耗时 | 204.6s 的歌用 **83s**（约 2.5× 实时，纯 CPU） |
| 内存 | `dim_f=3072` 的模型在 8 线程机器上 `bad allocation`，必须用 `dim_f=2048` |

### 坑：模型输出哪一轨，不能看文件名

`UVR_MDXNET_3_9662.onnx` 名字里没有 `Inst`，但它输出的**是伴奏**。
按文件名猜（含 `Inst` 才算伴奏）会把整条链路的人声/伴奏标签写反，
而且**看不出来**：两轨长度、能量占比、编码结果全都正常，只有耳朵能发现。

这个坑踩过两次。第二次是在 C1 接到曲包之后——混音条上「人声」那一路其实是伴奏，
拉到底听到的才是人声。

现在 `--target auto` 改成实测：伴奏有 kick 和 bass，30–120Hz 能量占比很高；
人声这一频段几乎是空的。

| 轨 | 30–120Hz 占比 |
|---|---|
| 真正的伴奏 | 47.5% |
| 真正的人声 | 0.0% |

阈值取 15%，两边都留了很大余量。另一轨一律用 `mix - 该轨` 得到。
`--target` 仍可显式覆盖（比如换模型后先看一眼打印出来的占比）。

### 实测结论：分离没有改善歌词对齐

拿同一首有标准答案的歌对比（探针行是独立做词级时间得到的）：

| 指标 | 混音 | 分离出的人声 |
|---|---|---|
| 探针行平均绝对偏差 | **0.07 s** | **1.42 s** |
| 插值行 | 3 / 73 | 26 / 73 |

**分离后反而更差**。原因不是分离质量，而是 Whisper 的行为：
这首歌开头 6–20 秒是密集重复的吟唱，混音上 Whisper 的重复锁定到 20 秒为止，
分离出干净人声后锁定**延长到 30 秒**，把后面所有锚点整体往前拖了 3–4 秒。

所以「必须先分离人声才能对齐」这个假设在本流程下**不成立**：
瓶颈是 Whisper 处理重复演唱的方式，不是伴奏干扰。

分离本身仍然必做——它是「伴唱 = AI 陪唱」的硬前置，只是别指望它提升歌词时间。

## 编舞生成（`build_choreo.py`）

按节拍网格 + 实测能量曲线，把动作库拼成整首的时间轴。

```powershell
python tools\build_choreo.py `
  --pack public\songpacks\demo\pack.json `
  --audio public\songpacks\demo\stems\instrumental.mp3 `
  --out public\songpacks\demo\actions.json
```

输出和手写版 `actions.json` 完全同构，运行时不用改。

| 步骤 | 做法 |
|---|---|
| 能量 | 逐小节 RMS → 10/90 分位归一到 0..1 → 3 小节平滑 |
| 乐句 | 2 小节一个乐句，按能量档位 calm / mid / high / peak 选模式 |
| 段落 | 同一曲线再平滑到 5 小节，按三档（静/中/响）切段，短于 4 小节并入相邻段 |
| 循环动作 | `dance.bounce` 没有固定时长，必须显式发 `stop` 指令收尾 |

**段落名只是响度分档，不是真实曲式**：主歌副歌要靠和声和旋律判断，
只看 RMS 分不出来。名字给 HUD 用，别当成音乐分析结果。

### 坑：`interrupt: 'none'` 的动作会静默吃掉下一个动作

`dance.spin` 的 `interrupt` 是 `none`，而 `base` 层是互斥层。它 1.3 秒播完之后
还要按 `blendOut`（0.25s）淡出，这段时间里仍然是「正在跑且不可打断」，
后面紧接着安排的 `dance.bounce` 会被 `ParamBus.play()` 判定成 `blocked` 直接丢弃——
而调用方（`TrackPlayer.onPlay`）没检查返回值，于是表现成「转完圈之后就再也不动了」。

生成器现在的做法是：转圈后延后 `动作时长 + 淡出` 再起跳。
更彻底的办法是让 `ParamBus` 在一次性动作超时后立刻释放互斥，
或者让 `TrackPlayer` 检查 `play()` 的返回值并补发。

## 无歌词路径（`auto_lyrics.py`）实测

同一首 ギンギラ，盲跑（不给任何歌词），再拿 P1 的结果当标准答案打分：

| 指标 | 有歌词（P1） | 无歌词（P2） |
|---|---|---|
| 文字覆盖 | 100%（歌词是输入） | **39.5%** |
| 时间误差中位数 | ~0.6 s（对着人工打点） | **0.25 s** |
| 时间误差 ≤1 s | 89% | 91% |

两条路径的误差形态正好相反：

- **有歌词**：文字绝对正确，时间靠 ASR 锚点推，误差来自锚点插值
- **无歌词**：时间就是 ASR 的词时间，很准；但**文字错得多**，
  `give lead` 被听成「ギリギリ」、`諸悪の権化` 听成「次回の季節」这种

**结论：39.5% 的文字覆盖率不足以直接交付。** 必须先把人声分离出来
（方案里的 B 阶段）再转写，混音里的鼓点和和声会显著拖垮 ASR。
分离本身也是「伴唱 = AI 陪唱」功能的前置条件，早晚要做。

### 无歌词路径踩到的两个坑

1. **置信度过滤会误杀歌声**。方案原本写的 `no_speech_prob > 0.6`、
   `avg_logprob < -1.0` 过滤，实测把 50 段砍掉 24 段，凭空造出 130 秒「空洞」，
   反而触发大量无用重转写。现在默认只过滤黑名单短语，`--strict-filter` 才开。
   这和 VAD 不能用是同一个原因——这些指标都是为语音训练的。

2. **重复检测要跟长度挂钩**。`ギリギリギリギリ…` 这种幻觉，词级检测抓不到
   （每个词都不一样），得看 2-gram 重复次数。但固定阈值会误杀正常歌词
   （100 字的段落里「でも」重复 6 次很常见），所以阈值取 `max(6, 长度×0.18)`。

3. **真重复和假重复分不开**。这首歌的副歌本来就是重复的，
   重转写后仍然「重复」→ 被判为幻觉丢弃，于是开头 7 行维持原样。
   这是方法本身的边界，不是 bug。

## 假名 / mora（`kana.py` + `build_units.py`）

> **2026-11-09 改动**：`mora_positions` 现在**只按 ASR 词的时长累加**，词与词之间的
> 空隙（间奏、长换气）不再摊给前一个 mora。之前一行 2 秒的 mora 就是这么来的。
> 效果：剣花 >1.0s 的 mora **12 → 0**（最大 7.01s → 0.99s）；白花 14 → 5。
> 另有可选 `--vocals`：用分轨浊音掩码把 mora 映射到有声段（收益小，默认不开）。

### 为什么要单独一层假名

1. **读音比汉字准**。ASR 选错汉字多数时候是近音判断失误，读音本身接近。
   丢掉汉字只留假名，等于丢掉了 ASR 最容易出错的那一层。
2. **假名就是 mora**，而 mora 是日文口型的单位——一个 mora 一个元音口型。
3. 日文是 **mora-timed** 语言，同句内每个 mora 时长几乎相等，
   所以「行时长 ÷ mora 数」比「按字符数均分」准得多
   （`所業` 两个字读 4 个 mora：しょ / ぎょ / う）。

同一份 P2 输出，只改比对方式：

| 比对方式 | 文字覆盖 | 时间误差中位数 |
|---|---|---|
| 汉字（原样） | 39.5% | 0.25 s |
| **假名（只比读音）** | **59.5%** | 0.33 s |

覆盖率相对提升 50%，时间几乎没损失。
**结论：无歌词路径的错误主要来自选字，不是听音。**

`compare_lyrics.py --kana` 可以复现这个对比。

### 日式英语：英文直接当片假名

日语歌里的英文基本是按片假名读的。实测这首歌：

- `give lead` 唱出来是**ギリギリ**（不是 ギブ リード）
- `give me give love` 听起来像**ギンギラ**（就是曲名）

所以不做英文 G2P，直接查一张英→片假名表（`kana.py` 的 `_EN_TO_KATA`），
当成假名参与 mora 切分。这比按英语音标处理更贴近实际发音，也不需要新依赖。
未收录的词保持原样、后续被丢掉——宁可没有，也不要读错。

加这一层之后 units 从 60/73 行涨到 **73/73 行**。

### 生成 units

```powershell
python tools\build_units.py `
  --lyrics public\songpacks\demo\lyrics.auto.json `
  --words .tmp\asr.words.json `
  --out public\songpacks\demo\lyrics.units.json
```

一条 unit：

```json
{ "t": 22.74, "d": 0.15, "ch": "しょ", "v": "i" }
```

`v` 直接对应 VRM 表情：`a→aa` `i→ih` `u→ou` `e→ee` `o→oh`，
`n` 是拨音（闭口），空串是促音（停顿）。

本机实测（ギンギラ）：

| 指标 | 数值 |
|---|---|
| 有 units 的行 | **73 / 73** |
| mora 总数 | 1015 |
| 单 mora 时长中位 | 0.163 s |
| 元音分布 | 以 a / i 为主，符合日文元音频率 |

行末时间优先用 ASR 词时间确定「这一行实际唱到哪」，而不是「下一行行首」——
后者会把间奏算进去。同时硬压到下一行开始之前，否则 ASR 词映射跨行时
units 会和下一行重叠（实测不夹紧会有 17 行越界）。

### 在渲染层怎么用

`src/songpack/viseme.ts` 的 `VisemePlayer` 把 units 摊平成一条时间轴，
每帧二分查当前 mora 的元音。`createLipSyncClip` 拿到元音后：

- **元音决定嘴型**（aa / ih / ou / ee / oh）
- **音量包络决定张合幅度**

两者相乘。所以静音、换气、间奏时嘴自然会闭上，不会出现「一直张着嘴」。
没有 mora 数据时退回纯包络驱动，行为和之前一样。

`pack.json` 里用 `assets.units` 指向文件；HUD 会显示当前口型。

### 行内分配：相对位置，不是绝对时间

早期版本直接用 ASR 词时间给每个 mora 定绝对时间，结果两个问题：

1. 词时间偏短时，一行 20 个 mora 挤在 1 秒内，**高亮提前结束**、嘴提前闭上
2. 词映射稀疏时（重复幻觉段），会造出好几秒的单个 mora

现在的做法是：**跨度**和**份额**分开算。

- **跨度** = 「第一个 ASR 词的开头」→「最后一个词的结尾」，行首不再用 LRC 的 `at`
  （LRC 行首普遍比人声早 100~300 ms）。没有词数据时退回「本行行首 → 下一行行首」。
- **份额** = 每个 mora 占这段跨度的比例，按**词的时长**累加，**词与词之间的空隙不计入**。
  缺口（间奏、长换气）会被按比例摊给所有 mora，但不会全砸给某一个——
  早期版本把 2 秒空隙全摊给前一个 mora，造出 2 秒一个的嘴型（白花第 10/20 行），
  就是这么来的。

> **这里踩过两次坑，方向相反，都记一下**：
> ① 跨度用「下一行行首」→ 行尾的间奏被算进演唱，mora 被拉长；
> ② 跨度用「词长之和」（等于把空隙切掉）→ 人声还在响、但已经没有 mora 覆盖，
> 实测白花**漏唱 33%**、剣花 26%（见 `tools/lip_audit.py`）。
> 正解就是上面这两句话：**跨度含空隙、份额不含空隙**。

外加三道保险：

- **覆盖率混合**：`alpha = 有效映射的 mora 数 / 总数`，
  和均分按 alpha 混合。映射稀疏时自动退回均分，不会更糟。
- **份额压缩**：权重取 0.7 次方再归一化，把离群份额往下拉。
- **份额上限**：单个 mora 最多占整行 35%，超出的部分按比例分给其他 mora。

效果（ギンギラ，1015 个 mora）：中位 0.157 s、越界行 0、
最大离群从 3.46 s 压到 1.67 s。`甘美なる 罰を` 的最后一个「を」从均分的
0.46 s 变成 **1.01 s**——这正是「长音口型时间不够」的直接修复。

**注意**：`--words` 必须用**精修后**的转写缓存。
精修前的缓存在重复幻觉段是坏的，行内分配会退化。
`auto_align.py` 现在会在精修后自动把缓存写回。

### 口型审计（`lip_audit.py`）

units 好不好只能靠看/听，而看一次要开应用、找那一段、盯几十秒。
`lip_audit.py` 把能测的都测了——拿**分轨人声**当真值：

| 指标 | 含义 |
|---|---|
| `miss` | 人声有声、但没有 mora 覆盖的帧占比（渲染时退回固定的「啊」嘴型） |
| `idle` | mora 覆盖、人声静音的帧占比（嘴在动但没唱） |

### 拗音元音（已修）

`しょ` 读 **sho**，元音是 o 不是 i。早期实现取首字的元音，
所以 `しょ`→i、`きゃ`→i、`しゅ`→i **全都错了**，影响所有拗音。
现在看末尾的小字（ゃ→a、ゅ→u、ょ→o）。

## 行首对齐：默认按读音比

歌词字符和 ASR 词做序列比对时，**默认先都转成假名**（`--text-align` 可切回原文本）。

原因很实在：ASR 听错的时候，错的往往是**汉字选择**，读音反而接近。

| 歌词 | ASR 听到 | 说明 |
|---|---|---|
| 衝動的 | 昭和の敵 | しょうどうてき / しょうわのてき |
| 照れくさい | そっとばっき | てれくさい / そっとばっき |

按读音比之后，第 19–21 行从偏 2.5 秒修到与独立词级探针完全吻合。

**但重复区处理不了「一对多」**。开头 6–20 秒里「ラルラ レイレイ ア ランラ レイ」
出现了十几遍，歌词只写了 4 行——「哪一遍对应哪一行」无从确定，
逐词锚点只会随机落在某一遍上。

> 注意：Whisper 的 `compression_ratio_threshold` 判据对这一段会整窗拒绝，
> 但那只是说「文本高度重复」，**不代表是幻觉**——这首歌本来就在重复。
> 不能拿它当幻觉证据。

现在的做法是：识别出这种高度重复段后，**把落在里面的连续行按行数在该段内均匀铺开**。
这不是最优解，但期望误差比随机锚点小，也不会出现某一行被拉到 20 秒之外。

反向踩过的坑：**零时长词不能当锚点**。Whisper 在幻觉段会吐出一串
`start == end` 的词（实测 23.30 处有 8 个），整行会锚到同一个点上。
现在构建字符映射前会过滤掉时长 < 20ms 的词。

## 两轮精修（这是精度的关键）
整首一次性转写时，Whisper 对唱歌有两个典型故障：

1. **重复幻觉**——同一个词连吐几十遍，时间全挤在几秒内。
   实测 93.54–98.00 s 吐了 70 多个「愛は」，而真实歌词在那一段完全没进去。
2. **整段静默**——68.02–93.54 s 整整 25 秒没有任何输出。

两种情况下那一段歌词都没有可用锚点，行级时间会塌到一个点上。
解决办法是「整首跑一遍 → 找出可疑区间 → 只重转写这些区间」：

| 轮次 | 触发条件 | 手段 |
|---|---|---|
| 第一轮 | 段间空洞 > 6 s、同词连续 > 5 次、连续 ≥3 行插值 | 10 s 窗 / 5 s 步进重转写 |
| 第二轮 | 仍然连续 ≥2 行插值 | 同上，另加歌词原文当 `initial_prompt` |

第二轮很关键：`give me give love` 整段被听成「元気だ 君の不変のカルマ」，
拿歌词当提示词之后才正确落到 169.98 / 171.56 / 171.96。

关掉精修用 `--no-refine`。

## 已知限制

1. **VAD 必须关闭**（脚本默认关）。
   Silero VAD 是语音模型，唱歌 + 伴奏会被判成非语音直接丢掉：
   实测词数从 831 掉到 185，大段歌词没有锚点。需要时用 `--vad` 显式开启。

2. **开头 7 行仍然靠手工**。
   `give lead ×2` + `ラルラ レイレイ ×3` 这七行是同一段旋律的重复，
   自动对齐给的结果把 1.7–10.7 s 空了出来，反而不如耳朵。
   这几行用 `K` 打点后会被标成 `src=user`，以后重跑不会动它。

3. **重复句是薄弱环节**。
   同文本重复出现时，字符级 LCS 容易串位。两轮精修能缓解，但不保证。
   判断方法：看输出里有没有连续多行被标成 `interp`。

4. **`small` 对日文快歌上限明显**。
   `medium` 更准（770MB，慢约 3 倍）。两轮精修之后 `small` 已经够用，
   再往上换模型收益不明显。

5. **曲包时长要三处一致**。
   `pack.json` 的 `duration`、`actions.json` 顶层的 `duration`、音频实际长度。
   **`actions.json` 的会覆盖 `pack.json` 的**——本项目就踩过这个坑：
   两份都写 90 而音频是 204.6 s，结果后半首歌放不出来、歌词全被截断。
   现在应用启动时会检查三处并对不一致报警。

6. **结尾 197–205 s 的重转写会失败**（仍然重复），保留原结果。
   那一段没有歌词，不影响。

## 动作：BVH → VRM（`bvh_to_clip.mjs` + `calibrate_hips.mjs`，2026-11-15）

```bash
# 0) 换模型时先导静止朝向表（脚掌朝向修对了，见 docs/motion.md 六「修二」）
node .tmp/serve.mjs 8791 dist
node tools/dump_rest_dirs.mjs http://127.0.0.1:8791 tools/motion/text.rest.json

# 1) 生成 clip（源 + 朝向表 + 标定表都在 tools/motion/ 下，可复现）
node tools/bvh_to_clip.mjs --bvh tools/motion/walk.bvh --trim 1 \
  --rest-dirs tools/motion/text.rest.json \
  --hips-cal tools/motion/walk.hips.json \
  --id gen.walk --name 走路 --out src/actions/gen/walk.ts --report   # --report 只看映射不写文件

# 2) 换模型 / 改完生成器之后，重新量一次「脚离地多少」（要先 build + 起服务器）
node .tmp/serve.mjs 8791 dist
node tools/calibrate_hips.mjs http://127.0.0.1:8791 gen.walk 2 tools/motion/walk.hips.json 67
```

| 参数 | 作用 |
|---|---|
| `--retarget aim-legs` | 腿**保世界方向**重定向（默认）；`aim` = 全身、`local` = 老做法（局部旋转共轭） |
| `--rest-dirs <json>` | 用真模型量出来的**静止朝向表**替代内置表（脚掌必须用，否则多转 90°） |
| `--arm-out <rad>` | 上臂外扩（默认 0.1 ≈ 5.7°）：源的摆臂贴身体，宽松衣服/裙摆会穿模 |
| `--owns-exclude <bones>` | 不归这条 clip 管的骨骼（默认 `head,neck`）：动捕的颈姿前倾 15°，淡入时会把脖子甩出去 |
| `--trim N` | 扔掉开头 N 帧。捕捉数据常垫一帧站立静止帧，留着会让髋一帧掉 4 cm |
| `--hips auto/source/none` | 髋位移来源：合成（默认，源没有根位移时）／照搬源根位移／全部置零 |
| `--hips-cal <json>` | 用真模型上量出来的表覆盖垂直位移**和位移速度**（推荐，见下） |
| `--no-base-pose` | 不扣 `VRM_BASE_POSE`（给没有 basePose 的占位角色用） |

**为什么需要两套髋位移推导**：

- 纯旋转重定向下，「源里腿弯了多少」推不出「VRM 上脚离地多少」——髋宽、
  有没有单独的髋关节骨、腿长比例都不一样。用源骨架 FK 推出来的曲线形状是对的，
  但整段会浮空约 4 cm（实测 120–146 mm，站姿基线 100.7 mm）。
- 所以在**真模型**上量：关掉 IK 逐帧读 `leftFoot/rightFoot/hips` 的世界 Y，
  `需要髋位移 = restAnkleY − (脚−髋) − hipsRestY`。表存成 JSON，生成时读入。
- 量测偶尔会撞上加载中的一帧（髋瞬移半米），生成器会按中位数剔掉离群值。

已知：这套表只对 `models/text.vrm` 有效。换模型要重量（占位角色的腿长是编的，
量了也没意义）。生成的 `walk.ts` 头注释里会写明用了哪个表。

标定表里还存了每帧**两只脚的 z**，生成器据此算 `travel`（米/秒）——
「单脚在一次支撑期里从最前退到最后」= 一步，一个周期两步。引擎就是按这个速度推窗口，
支撑脚在世界里才是静止的（不滑）。写进 clip 的 `travel` 只表示速度，不含坐标。

`calibrate_hips.mjs` 要求页面**已经稳定**（启动流程会插一段问候动作，髋会蹲下去半米），
所以它连续读两次、两次一致才采信；撞上半米误差的样本会按中位数剔掉。

**为什么是循环 clip**：走路是周期动作，如果写成「播完再 play 一次」，同一个 id 重放
会在接缝掉 1–2 帧（腿静止 ~150 ms，窗口还在平移，看着像飘）。所以生成的 clip
`duration` 是无穷、`sample` 里用 `t % CYCLE` 自己绕；`cycle` 字段告诉引擎一个周期多长，
由引擎决定走几个周期后 `stop`。

**已知缺口**：这只对「原地」动作成立。换成真正带根位移的捕捉数据，`travel` 应该来自
根关节的水平位移、髋位移只留上下；生成器目前在检测到根位移时会照搬源根位移进 hips
（角色在场景里滑、窗口不动）。手上没有那种 BVH，所以没写没测。

**起步前只拉直腿**：`startWalk()` 只把两条腿的增量压到 0，头/颈/胸/手保持作者摆的角度。
早先是全身归零，头部会从 −10.3° 掉到 0、prep 结束又回到 −10.3°，再被走路 clip 拉到
+1.6°——一次起步点了两下头。实测修好后 prep 全程头 −10.3°，只在走路淡入的 0.25 s 里
单向走到 +1.6°。

## 曲子的心情 / 氛围（`song_mood.mjs`，2026-11-16）

用户调查里冒出来的新方向：听一首歌，判断「它想表达什么心情、营造什么氛围」。
第一版只吃**曲包里已有的东西**（`pack.json` 的 BPM + `work/f0.json` 的音符表
`[起点, 时长, MIDI]`），不解码音频，几毫秒跑完。

```bash
node tools/song_mood.mjs --all                                  # 所有曲包一览
node tools/song_mood.mjs public/songpacks/<id>                  # 单个，打印细节
node tools/song_mood.mjs public/songpacks/<id> --write           # 写 <pack>/mood.json
```

输出两维（`valence` −1 忧郁 … +1 愉快、`arousal` 0 平静 … 1 激动）+ 调性 + 粗标签。
为什么是两维：这两维有公开标注集（DEAM / PMEmo）可校准；「燃 / 治愈 / 丧」这种 8 类标签
没有可靠标注，算出来也没法验。

| 曲包 | BPM | 调性 | valence | arousal | 词 | 标签 |
|---|---|---|---|---|---|---|
| demo | 167.9 | D 大 | +0.64 | 0.80 | 热烈 | 燃/上头/大调 |
| 剣花（七魔剑 OP） | 138.7 | A 大 | +0.42 | 0.70 | 热烈 | 燃/上头/大调/跳进多 |
| CHAINSAW BLOOD（电锯人 ED） | 147.0 | E 小 | −0.35 | 0.68 | 紧绷 | 冲/压迫/小调 |
| 想風（药师少女 插曲） | 113.9 | C# 大 | +0.52 | 0.56 | 明快 | 轻快/大调 |
| 白花（异修罗 ED） | 88.0 | A# 小 | −0.44 | 0.41 | 压抑 | 克制/小调/上行 |

**特征**：音级直方图（按时长加权）→ Krumhansl-Schmuckler 24 个调里取最佳（附置信度）；
中位/加权平均音高、P10–P90 音域；音程（跳过跨休止 >1.5 s 的换句）的级进/跳进/上行比例；
前后半段平均音高差（轮廓）；出声占比、音符数/秒、平均音长、短音比例、踩拍比例。

**权重**（启发式，不是训练出来的）：

| 维度 | 组成 |
|---|---|
| arousal | BPM 0.50 · 平均音程 0.22 · 中位音高 0.16 · 出声占比 0.12 |
| valence | 调式 0.46 · BPM 0.16 · 轮廓 0.14 · 中位音高 0.12 · 上行比例 0.12 |

**故意没用音符密度**：f0 的切分把连音/滑音切碎，白花（88 BPM 慢歌）的 notes/s 反而比
147 BPM 的 CHAINSAW 高，当「能量」会把慢歌推高。等接了真正的起音检测再说。

**已知局限**：

- 只看主旋律。很多「悲伤」和「温柔」在旋律上几乎一样，区别在音色和编曲 → `valence` 只当提示；
- 没接唱词情绪（`lyrics.units.json` 里有时间戳，可以另做一条 LLM 线）；
- 只有 5 首对照，`valence` 的排序还没有经过用户盲评；真要数字得拿 DEAM / PMEmo 拟合；
- **还没接界面**：没有灯光 / 镜头 / 动作强度，`mood.json` 也还没写进曲包。
**应用内也有一份**：`src/songpack/mood.ts` 直接从渲染进程已经载入的参考音高轨算同一套特征
（先把逐帧基频切成音符），所以不用等 `mood.json` 就能用。它已经接进灯光：右键
「灯光 → 跟随曲子（按旋律的情绪）」。三首实测（应用内 / 离线）：

| 曲包 | valence | arousal | 调性 | 灯 |
|---|---|---|---|---|
| 白花 | −0.37 / −0.44 | 0.48 / 0.41 | A# 小调 | 冷、暗 |
| 剣花 | +0.57 / +0.42 | 0.75 / 0.70 | A 大调 | 暖、亮 |
| CHAINSAW | −0.30 / −0.35 | 0.75 / 0.68 | E 小调 | 中性偏冷、边缘光强 |

离线用流水线产出的音符表）。要更准就得把这套特征拿去 DEAM / PMEmo 拟合。
