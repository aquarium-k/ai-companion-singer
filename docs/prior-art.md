# 同类项目在做什么（以免重复造轮子，也别误以为自己原创）

> 2026-11-15。目前只认真看过一个：[xiaoke.ai（小可爱）](https://github.com/liupig/xiaokeai)，
> 依据是作者自己发的[技术路线长文](https://juejin.cn/post/7695613822451990578)（不是猜的）。
> 目标：**动作**和**口型**这两块别人是怎么做的、我们哪里不一样。

## 一、xiaoke.ai 的动作是怎么来的

**结论：全是「预先存在」的动作，没有生成式动作。**

| 类别 | 做法 | 关键限制 |
|---|---|---|
| 舞蹈 | `[dance:xxx.vmd]` 播 **VMD 文件**（MMD 的动作格式） | **只支持 PMX 模型**；VRM / GLB 直接提示不支持 |
| 打招呼 / 点头 / 摇头 | `[act:nod]` `[intent:…]` → 库里**审过的**动作片段 | 模型只能点名，不能编舞 |
| 待机 | 空闲时角色自己走动（预设闲置动作） | — |
| 动捕 | MediaPipe Holistic 在 Worker 里出全身+双手+脸，解成父骨骼四元数，静止抖动用 1€ Filter | 开动捕时 VMD 和闲置动画都暂停 |
| 镜头 | 景别 × 运镜 × 站位 × 动作 的组合进了**审查表（三万多条）**，只有验证过不穿模的组合才能上场 | 相当于用人工审核替代碰撞检测 |

两条值得学的：

1. **「组合审查表」**比实时避碰便宜，而且效果稳。我们现在是 P9 脚部锁定 + 世界坐标手臂 IK
   （实时解算），更"硬"，但**曲包之间的动作复用**没有他们那套审查流程。
2. **动作靠资源包扩充**（导入 VMD / 模型带动作），代码只负责播放。我们的动作库是代码生成的
   （关键帧剪辑 + 姿势库），扩充靠写代码/摆姿势，慢但可控。

## 二、口型：他们是 RMS，我们是 mora

文章中明确写「口型不认音素……对时域波形算 RMS，放大后驱动张嘴，嘴跟着这句话有多响，
不跟着声母」。我们的做法是**逐 mora 的元音口型（あいうえお）**，从 C2 起就是。

所以口语/说话场景他们的够用，**唱歌场景他们做不了**（唱长音时嘴会一直半开）。
这一块我们是领先的，但要记住：**领先不等于创新**——VOICEVOX 那类 TTS 也能给出 mora 口型，
我们真正的差异是「口型/咬字/和声共用一个从歌里反推出来的 mora 时间轴」。

## 三、对我们决策的影响

1. **「动作 in-betweening」暂时否决是站得住的**：连这类成熟项目都没做生成式动作，
   而是靠资源包 + 人工审查。我们做 in-betweening 的投入产出比更低。
2. 但**可以抄他们一个便宜的做法**：把「曲包 × 动作 × 站位 × 镜头」的可用组合**离线审一遍**
   存成表，运行时只从表里挑。比现在的运行时 IK 兜底更稳，工作量小。
3. 他们有、我们没有的（按价值排）：
   - 现成的 VMD 舞蹈资源生态（我们的编舞是程序生成的，没有"跳舞"这一档）；
   - 实时动捕输入（MediaPipe）——桌宠场景下意义不大；
   - 记忆（mem0 + 向量库）、塔罗这类"陪玩"内容——和我们的方向不同。
4. 我们有的、他们没有的：**唱歌**（fl 唱/和声/跟唱判定/翻唱）、**曲包流水线**、**逐 mora 的口型与咬字**。
