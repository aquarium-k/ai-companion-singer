# 全自动歌词流水线 · 方案

> 状态：P1 已交付；P2 实现并测过，**已决定暂不采用**；假名/mora 层（P3 前半）已完成
> 目标：用户丢进一首歌，本地全自动产出可用的 `.songpack`，不要求用户准备任何文字材料

---

## 0. 目标与非目标

**目标**

- 输入：任意音频文件（mp3 / flac / wav / m4a），**不需要歌词**
- 输出：`public/songpacks/<id>/` 下的完整曲包（分轨、歌词时间轴、口型数据、编舞）
- 全程本地运行，不依赖云端 API
- 覆盖中 / 日 / 英三种语言

**非目标（现阶段）**

- 不做人的音色克隆
- 不做和声/对唱
- 不追求逐字的演唱评分（那是反馈层的事）

---

## 1. 核心判断

### 1.1 「有歌词」和「没歌词」是两条路径，但出口相同

| 情况 | 文本来源 | 时间来源 |
|---|---|---|
| 用户提供歌词 | 直接用 | **强制对齐**（文字 + 音频 → 时间） |
| 用户没提供 | **ASR 转写** | 转写自带的 segment/word 时间戳 |

两条路径都产出同一种中间结构（`lines[]` + 可选 `units[]`），下游完全一致。

**有歌词时优先用对齐**，因为 ASR 的错字和漏句会污染结果；但没歌词时 ASR 就是唯一选择。
所以流水线的默认假设是「没有歌词」，有则走捷径。

### 1.2 人声分离：已实现，但**没有**提升对齐精度

原方案断言「强制对齐和 ASR 在混音上都会显著退化，分离是前置条件」。
A1 做完后用同一首歌做了对照实验，结论推翻了一半：

| 指标 | 混音 | 分离出的人声 |
|---|---|---|
| 探针行平均绝对偏差 | **0.07 s** | **1.42 s** |
| 插值行 | 3 / 73 | 26 / 73 |

分离后对齐**更差**。原因不在分离质量，而在 Whisper：
开头 6–20 秒是密集重复的吟唱，混音上重复锁定到 20 秒为止，
干净人声上锁定延长到 30 秒，把后面锚点整体拖早 3–4 秒。

所以「分离 → ASR 更准」只在伴奏确实掩盖人声时成立；
本曲的问题在重复演唱，分离帮不上忙反而放大。

分离仍然必做：它是「伴唱 = AI 陪唱」的硬前置（见 `tools/separate.py`）。

### 1.3 逐字口型的关键难点是「读音」，不是「时间」

日文歌词是汉字，`酷く淡い` 要变成音节必须知道读音（く / く / あ / わ / い）。
所以 `units[]` 的生成是「分词 → 注音 → 按 mora/phoneme 切分 → 分配时长」，
纯靠时间戳是拆不出音节的。

## 2. 流水线

```
                 ┌─────────────┐
  音频文件 ──────▶ │ A. 解码/归一 │
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ B. 人声分离  │  Demucs → vocals.wav / inst.wav
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ C. 文本获取  │  有歌词: 跳过
                 └──────┬──────┘  无歌词: faster-whisper → lines[] + 时间
                        ▼
                 ┌─────────────┐
                 │ D. 强制对齐  │  已知文本 + vocals → 词级时间戳
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ E. 音节化    │  分词 + 注音 → units[{t, d, ch, vowel}]
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ F. 口型映射  │  vowel → aa/ih/ou/ee/oh
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ G. 编舞生成  │  节拍/段落 → ActionTrack
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐
                 │ H. 打包      │  .songpack
                 └─────────────┘
```

### A. 解码与归一

- ffmpeg 解码为 44.1kHz 单声道（分离用）和立体声（播放用）
- 响度归一化（LUFS），避免不同歌差异过大
- 产出：`decoded.wav`

### B. 人声分离

- **Demucs v4 (`htdemucs_ft`)**，两轨模式（vocals / no_vocals）
- 产出：`stems/vocals.wav`、`stems/instrumental.wav`
- **质量闸门**：检测人声轨的能量占比。低于阈值说明分离失败或本来就是纯音乐，
  直接标记「不可用」而不是硬跑下去。

### C. 文本获取

**C1 有歌词**：直接进 D。

**C2 无歌词**：`faster-whisper` + `large-v3`

- 输出 segments（起止时间 + 文本）和 word timestamps
- **歌词行切分**：Whisper 的 segment 是按停顿切的，通常接近乐句，但不等于歌词行。
  合并规则：相邻 segment 间隔 < 0.35s 且合并后长度 < 25 字符 → 合并；
  超过 2s 的停顿 → 强制断行。
- **幻觉过滤**（关键）：
  - `no_speech_prob > 0.6` 的段丢弃
  - `avg_logprob < -1.0` 的段标记低置信
  - 结尾 15 秒内出现与正文重复的句子 → 大概率是幻觉，丢弃
  - 纯音乐段可能被编造成「谢谢观看」之类，用高频幻觉短语黑名单兜底
- 语言检测：`language` 自动识别，中日混排时按字符集分段处理

### D. 强制对齐

- **stable-ts `align()`**（内部用 Whisper 的 cross-attention + wav2vec2）
- 输入：干声 + 已知文本（逐行）
- 输出：每个词/字符的 `start` / `end`
- 备选：WhisperX（对齐更稳，但依赖更重）、MFA（最准，需要词典和额外安装）

**对齐失败的兜底**：逐行用 ASR 的 segment 时间按字符数比例分配。
精度掉到 ±300ms，但至少能用。

### E. 音节化（决定口型质量的一步）

不同语言三条支路：

| 语言 | 分词 | 注音 | 音节单位 |
|---|---|---|---|
| 日文 | `fugashi` + `unidic-lite` | 片假名读音 | mora（きゃ = 1 mora） |
| 中文 | `jieba` | `pypinyin` | 汉字（声母+韵母） |
| 英文 | 空格 + `g2p_en` | CMU 音素 | 音节（元音为核心） |

**时长分配**：先按音节数均分该词的时长，再用能量/onset 微调边界（P3 优化）。
日文的 mora 时长基本均匀，均分已经够用；英文重音节要加权。

产出 `units[]`：

```json
{ "t": 12.34, "d": 0.18, "ch": "よ", "v": "o", "conf": 0.92 }
```

### F. 口型映射

- 元音 → VRM expression：`a→aa`、`i→ih`、`u→ou`、`e→ee`、`o→oh`
- 辅音（n/m/ng）→ 闭口或 `ou` 的弱化
- 过短单元（< 60ms）并入相邻单元，避免嘴抖
- 最终口型 = **音节形状 × 音频包络**（包络已经在跑）

### G. 编舞生成

不在本方案重点，但流水线要留位。当前用「动作库按节拍拼接」，
输入是 BPM、段落边界、能量曲线。

### H. 打包

写 `pack.json` / `lyrics.json` / `actions.json` / `stems/`，
并在 `pack.json` 里记录处理元数据（见 §5）。

## 3. 工具选型

| 环节 | 首选 | 备选 | 取舍 |
|---|---|---|---|
| 分离 | **MDX-Net ONNX**（`audio-separator`） | Demucs `htdemucs_ft` | MDX 模型 ~60MB、显存需求低；Demucs 质量更好但 2GB 显存吃紧 |
| ASR | **`faster-whisper` small int8** | medium int8 | small 权重 ~250MB，2GB 显存绰绰有余 |
| 对齐 | **`stable-ts` `align()`** | WhisperX / MFA | 复用已加载的 Whisper，**不额外下载 wav2vec2** |
| 日文分词 | `fugashi` + `unidic-lite` | `pykakasi` | fugashi 准，pykakasi 轻但注音粗糙 |
| 中文拼音 | `pypinyin` | — | 标准方案 |
| 英文 G2P | `g2p_en` | CMUdict | g2p_en 能处理词典外词 |

**关键取舍：不用 wav2vec2 对齐模型。** `stable-ts` 的 `align()` 可以直接复用 Whisper 的
cross-attention，避免再下 1GB+ 的日语对齐模型。精度略低于专用对齐器，但足够行级/字级使用，
且总模型体积压到 **300MB 以内**。

## 4. 本机基准与耗时

目标机器实测：**8 线程 CPU，NVIDIA MX450，2GB 显存（可用 1.9GB）**。

2GB 显存直接排除了 `large-v3`（int8 权重 1.5GB + 推理缓存放不下）。
按大小降级到 `small int8`，并用「复用 Whisper 做对齐」省掉额外模型。

### 模型体积

| 模型 | 体积 | 2GB 显存 |
|---|---|---|
| MDX-Net 人声分离 | ~60 MB | ✅ 宽裕 |
| faster-whisper small int8 | ~250 MB | ✅ 宽裕 |
| faster-whisper medium int8 | ~770 MB | ⚠️ 勉强（可选升级） |
| Demucs htdemucs_ft | ~320 MB | ❌ 大概率 OOM |

**默认总下载约 310 MB**，远低于 3GB 的上限。

### 耗时（4 分钟歌曲）

| 路径 | 组成 | 合计 |
|---|---|---|
| **有歌词**（跳过分离） | ASR 40–60s + 对齐 20–30s + 音节化 5s | **约 1.5 分钟** |
| **无歌词**（全自动） | 分离 90–180s + ASR 60s + 对齐 30s + 打包 | **约 3–4.5 分钟** |

**「有歌词就跳过分离」是达成 5 分钟目标的关键优化。**
混音对强制对齐的影响远小于对 ASR 的影响——对齐只是把已知文字贴到时间上，
伴奏会降低精度但不会导致失败；而 ASR 在混音上会直接崩掉。所以两条路径的分离需求不对等。

### 分离这一步的风险

MDX-Net 在 2GB 显存上需要分段推理（chunk）。如果仍然 OOM，降级到 CPU：
一首 4 分钟歌约 6–8 分钟，会突破 5 分钟预算，此时应提示用户而不是静默变慢。

### 4.4 运行策略：CPU 优先，GPU 可选

**建议默认全 CPU 跑，不折腾 CUDA。**

理由不是性能，是安装成本。Windows 上让 CTranslate2 / ONNX Runtime 走 GPU 需要
匹配版本的 CUDA runtime + cuDNN DLL，装错一个版本就是几小时的排查；
而 2GB 显存本来也只能跑小模型，收益有限。

CPU 路径的依赖很干净：

| 包 | 用途 | 体积 | 是否需要 torch |
|---|---|---|---|
| `faster-whisper` | ASR（CTranslate2） | ~120 MB | ❌ |
| `audio-separator` | 人声分离（ONNX） | ~60 MB | ❌ |
| `stable-ts` | 强制对齐 | ~40 MB | ✅（CPU 版 ~220 MB） |
| `fugashi` + `unidic-lite` | 日文分词注音 | ~50 MB | ❌ |
| `pypinyin` / `g2p_en` | 中英注音 | ~10 MB | ❌ |

**合计约 500 MB**（其中 220MB 是 CPU 版 torch，只在对齐时才用）。

8 线程 CPU 上的估算（4 分钟歌）：

| 环节 | 估算 |
|---|---|
| faster-whisper small int8 | 40–70 s |
| audio-separator（MDX-Net） | 60–120 s |
| stable-ts align | 30–60 s |
| 音节化 + 打包 | < 10 s |
| **全自动合计** | **约 2.5–4 分钟** |

这条路不需要 CUDA、不需要显卡驱动对齐，装完就能跑，且满足 5 分钟预算。
GPU 加速留作后续可选优化，不作为初版依赖。

## 6. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 分离失败 | 人声轨里全是伴奏，对齐全错 | 人声能量占比闸门，低于阈值直接判失败 |
| ASR 幻觉 | 间奏被编造出句子、结尾重复 | `no_speech_prob` / `avg_logprob` 过滤 + 黑名单 + 尾部去重 |
| 中日混排 | 分词错乱 | 按 Unicode 区间切段，分别走两条注音支路 |
| 演唱拖音/气声 | 字级时间漂移 | 以对齐结果为准，不用 ASR 时间；长音用能量峰值校正 |
| 现场版 / 变调 | 音高与录音室版不一致 | 先做调性估计，必要时移调后再对齐 |
| 纯音乐 / 无人声 | 全流程无输出 | B 阶段闸门直接判定，输出「仅伴奏」曲包 |
| 版权 | 曲库分发 | 用户自备音源，本地产物不联网、不分发 |

## 9. 异步执行与人工修正

### 9.1 异步作业模型

流水线是独立的 Python 进程，前端不阻塞：

```
用户拖入音频
   ↓
启动 tools/pipeline.py（后台进程，立即返回）
   ↓
前端每隔 1s 轮询 public/songpacks/<id>/job.json
   ↓
done → 自动载入曲包；failed → 显示失败阶段和原因
```

`job.json` 状态机：

```json
{
  "state": "aligning",
  "stage": 4,
  "stages": ["separate", "asr", "align", "units", "pack"],
  "progress": 0.62,
  "message": "对齐中 38/73 行",
  "startedAt": "...",
  "error": null
}
```

### 9.2 幂等与增量重跑

每个阶段的产物都落盘，重跑时按存在性跳过：

| 阶段 | 产物 | 重跑条件 |
|---|---|---|
| 分离 | `stems/vocals.wav` | 不存在或音频 mtime 更新 |
| ASR | `.work/asr.json` | 不存在 |
| 对齐 | `.work/align.json` | 不存在 |
| 音节化 | `lyrics.json` 的 `units` | 不存在 |

这样调参时不用每次从分离重来——分离是最慢的一步。

### 9.3 人工修正闭环

自动跑完不等于全对，必须留一个低成本的人工出口：

1. 每个 `line` / `unit` 带 `conf`（0–1）
2. `conf < 0.6` 的行在字幕上标高亮
3. 打点工具加一键「跳到下一个低置信行」（`N`）
4. 人工改完写回 `lyrics.json`，同时清掉 `pack.json` 里对应的 warning
5. **人工修正优先于重新跑流水线**——重跑成本几分钟，改一行是几秒

这比追求 100% 自动现实：自动处理 90–95%，剩下几分钟手工收尾。

## 11. 实施状态与实测修正

### 11.1 P1（有歌词 → 行级时间）：已完成

`tools/auto_align.py`。73 行里 63 行拿到真实 ASR 锚点，3 行插值，7 行人工。
关键结论：

- **VAD 必须关**。Silero VAD 会把唱歌判成非语音，词数从 831 掉到 185。
- **整首一次性转写会遇到两类故障**：重复幻觉（一个词连吐几十遍）、
  整段静默（实测有 25 秒没有任何输出）。这两种情况下那一段歌词没有锚点，
  行级时间会塌到一个点上。
- **解法是分窗重转写**：找出可疑区间，只重转写这些区间，时间立刻正常。
- **歌词当 `initial_prompt` 是最后一步杀手锏**：`give me give love` 整段
  被听成「元気だ 君の不変のカルマ」，加歌词提示后才正确落位。

### 11.2 P2（无歌词 → 全自动）：已实现，但**不可单独交付**

`tools/auto_lyrics.py`，用 `tools/compare_lyrics.py` 打分。同一首歌盲跑：

| 指标 | P1 | P2 |
|---|---|---|
| 文字覆盖 | 100%（歌词是输入） | **39.5%** |
| 时间误差中位数 | ~0.6 s | **0.25 s** |

误差形态相反：P2 时间更准（直接就是 ASR 词时间），但文字错得多。
**39.5% 不够用**，说明 §1.2「必须先分离人声」是对的。

### 11.3 对原方案的三处修正

1. **§2.C 的幻觉过滤阈值不能用。** `no_speech_prob > 0.6` /
   `avg_logprob < -1.0` 在带伴奏的歌声上把 50 段砍掉 24 段，
   凭空造出 130 秒空洞。原因和 VAD 一样：这些指标是为语音训练的。
   现在默认只过滤黑名单短语。

2. **§5 的 `conf` 字段暂时没做。** 行级置信度需要保留 word probability，
   而分窗重转写会丢掉它。更实用的替代是 `src` 字段
   （`asr` / `interp` / `user`），直接表达「这行的时间是怎么来的」。

3. **§9.3 的「低置信行」判据改成 `src=interp`。** 插值行比置信度分数
   更能反映真实风险——实测插值行的误差是锚点行的 10 倍以上。

### 11.4 假名层：已完成的意外收获

原本只是想做 P3 的注音，结果它先回答了 P2 的核心问题。

| 比对方式 | 文字覆盖 | 时间误差中位数 |
|---|---|---|
| 汉字 | 39.5% | 0.25 s |
| **假名** | **59.5%** | 0.33 s |

只换比对方式（都转成平假名），覆盖率相对提升 50%。
**说明无歌词路径的错误主要来自「选字」，不是「听音」。**
ASR 把 `所業` 写成 `処処`，读音其实接近；丢掉汉字这一层，噪声去掉一大半。

产物：

- `tools/kana.py`：汉字→平假名（pykakasi）、mora 切分、元音归类
- `tools/build_units.py`：歌词 + 行时间 → `units[{t,d,ch,v}]`
- 本机实测：60/73 行、858 个 mora，单 mora 时长中位 0.163 s

跳过 13 行英文为主的行（`give lead…` / `AH` / `poker face…`），英文需要 G2P。

### 11.4.1 修正：日式英语不需要 G2P

上面那句「英文需要 G2P」是错的。实测日语歌里的英文基本按片假名读：

- `give lead` 唱出来是**ギリギリ**
- `give me give love` 听起来像**ギンギラ**（就是曲名）

所以查一张英→片假名表就够了，当成假名参与 mora 切分。
比按英语音标处理更接近实际发音，也不需要新依赖。
加了这一层，units 覆盖从 60/73 行涨到 **73/73 行、1015 个 mora**。

### 11.5 决定：现阶段坚持「用户提供歌词」

无歌词路径即使加上假名层也只有 59.5% 文字覆盖，而且**没歌词时人耳听译同样不准**，
两条路都不可靠。所以现阶段：

- **歌词是必需输入**，P2 的代码保留但不推向产品
- 人声分离（P2.5）暂时不做，等「伴唱 = AI 陪唱」需要伴奏轨时再一起做
- 假名层留下来，服务 P3 的逐字口型——它本来就该有

### 11.6 P3 接线：已完成

`units[]` 已经接进渲染层，`tools/build_units.py` → `src/songpack/viseme.ts`
→ `createLipSyncClip`：

- 元音决定**嘴型**（aa / ih / ou / ee / oh）
- 音频包络决定**张合幅度**
- 没有 mora 数据时退回纯包络，行为和之前一致

`pack.json` 用 `assets.units` 指向数据文件，HUD 显示当前口型便于核对。

验证方法：查 27.1 s 的口型应为 `a`。第 9 行「正気じゃいられない 既に」
从 24.98 s 起 12 个 mora 均分 3.6 s（0.3 s 一个），第 8 个是「な」——
HUD 实测显示 `a`，与推算一致。

### 11.7 逐字高亮：已完成

和口型吃同一份 `units[]`，`VisemePlayer.lineProgress(start, end, time)` 给出 0..1 的进度。

实现上没逐字拆 span（中日文标点、假名拆开会断行错乱，每帧重建 DOM 也贵），
而是用 `background-clip: text` + 一段两色渐变做扫过，
每帧只改 CSS 变量 `--p`。CSS 变量在浏览器里算出来是
`linear-gradient(90deg, gold 0%, gold 65.2%, white 65.2%, white 100%)`，
已实测确认。

分母用 **mora 数**而不是字符数——`所業` 两个字读 4 个 mora，
按字符数算会让这两个字扫得比旁边慢一倍。

### 11.8 行内 mora 定位：已完成

早期 units 是行内均分，所以长音分不到足够时长。现在：

- **行的时间跨度永远铺满到下一行开始**——不然高亮会提前结束、嘴提前闭上
  （这就是「开头那句一下子就高亮完了」的原因）
- **只从 ASR 取 mora 的相对位置**，再映射回这段时间
- 映射不可靠时自动退回均分（覆盖率混合 + 份额压缩 + 35% 上限）

结果：`甘美なる 罰を` 的最后一个「を」从 0.46 s 变成 **1.01 s**。
单 mora 时长中位 0.157 s，越界行 0，最大离群从 3.46 s 降到 1.67 s。

顺带修了一个真 bug：**拗音元音全错**（`しょ`→i 应为 o、`きゃ`→i 应为 a），
影响所有 きゃ/しゃ/ちゃ/にゃ/ひゃ/みゃ/りゃ/ぎゃ/じゃ/びゃ/ぴゃ。

### 11.9 按假名对齐：行内和无歌词路径有效，行首要看区域

试下来结论是分区域的：

- **汉字听错的地方，假名对齐明显更好**。`衝動的` 被听成「昭和の敵」、
  「照れくさい」被听成「そっとばっき」——按读音比就能对上，
  第 19–21 行因此从偏 2.5 秒修到与词级探针完全吻合。
- **重复区属于「一对多」，任何逐词对齐都无解**。开头 6–20 秒里
  「ラルラ レイレイ ア ランラ レイ」出现十几遍，歌词只写了 4 行。
  哪一遍对应哪一行无从确定，逐词锚点只会随机落在某一遍上。

  > 修正：早前用 Whisper 的 `compression_ratio_threshold` 判据说这一段
  > 「是幻觉」，这个推断是错的。该判据只说明**文本高度重复**，
  > 而这首歌本来就在重复。不能把「重复」当「幻觉」。

  现在识别出高度重复段后，把落在里面的连续行**按行数在段内均匀铺开**。
  不是最优解，但不会出现某一行被拉到 20 秒之外。

所以现在**默认按假名对齐**，并用 `--text-align` 可以切回去。

同时修了一个坑：**零时长词不能当锚点**。Whisper 在幻觉段会吐出一串
`start == end` 的词（实测 23.30 处有 8 个），第 9 行就锚在了那里，
偏差 1.7 秒。现在构建字符映射前会过滤掉时长 < 20ms 的词。
